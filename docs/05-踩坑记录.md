# 05 踩坑记录

这里每个坑都是**真实撞过并修好**的，附现象、根因、实测数据和最终解法。
按"踩到的概率 × 排查难度"排序。

---

## 1. `.bat` 必须纯 ASCII

**现象**：双击 `.bat`，窗口里刷出一堆
`'…' is not recognized as an internal or external command`，
而且**同一份文件**每次跑失败的行还不一样。

**根因**：cmd.exe 解析批处理文件时按**字节偏移**定位每一行。文件里含多字节字符
（中文 UTF-8 占 3 字节）时，偏移会逐渐漂移，最终把某一行切在半个字符中间 ——
于是本该是 `echo 安装完成` 的那行被拆成了非法命令。

**实测**（同一份内容，`CMD /D /C <file>`）：

| 编码 | 大小 | 结果 |
|---|---|---|
| 纯 ASCII + CRLF | 5733 字节 | **69/69 行正常，stderr 全空** |
| UTF-8 无 BOM + CRLF | 8318 字节 | 只有 19/69 行，大量乱码命令 |
| GBK + CRLF | 5845 字节 | 正常，但与 Node 的 UTF-8 输出互相冲突 |
| UTF-8 with BOM | — | BOM 被当成命令名的一部分 |
| ASCII 外壳 `chcp 65001` 后 call UTF-8 内层 | — | 仍然 19/69，无效 |

**解法**：

1. `.bat` 只写纯 ASCII，永远是 `title` + `chcp 65001` + `node scripts\xxx.mjs` 这种薄壳
2. **所有中文提示由 Node 打印** —— Node 写的是 UTF-8 字节，配合 `chcp 65001` 显示正常
3. 连控制台窗口标题也用 Node 设置（OSC 转义序列 `ESC ] 0 ; <标题> BEL`），
   因为 `title 中文` 也是那行会被切掉的命令

放在 `scripts/bat-lint.mjs` 里做成了门禁（检查纯 ASCII + CRLF + 无 BOM），
`env-check.mjs` 每次也会顺带跑一遍。

## 2. MinGW 的符号导出上限

**现象**：链接阶段报 `export ordinal too large` 或
`too many exported symbols`，编译在最后一步失败。

**根因**：MinGW 构建 DLL 时**默认导出全部静态库符号**，而 Windows PE 格式限制
导出序号 ≤ 65535。Tauri 依赖的 `windows` crate 生成的符号数量远超这个上限。

**解法**：在 `src-tauri/.cargo/config.toml` 里加一个链接参数：

```toml
[target.x86_64-pc-windows-gnu]
rustflags = ["-C", "link-arg=-Wl,-exclude-all-symbols"]
```

它让链接器只导出显式标记的函数（Tauri 的 cdylib 只需要少量 FFI 导出）。

**注意**：网上常见的解法是装 LLD 并切 `-fuse-ld=lld`，**那是多余的** ——
GNU ld 2.4x 原生支持 `-exclude-all-symbols`，不需要额外下载 LLD。

这个文件由 `scripts/setup-gnu.mjs` 生成（探测 MinGW 真实路径后写出来），
手改会被覆盖。

## 3. WebView2Loader.dll 没进安装包

**现象**：装完双击启动，弹窗提示**找不到 WebView2Loader.dll**。
但去 `target/.../release/` 目录一看，这个文件明明就在 exe 旁边。

**根因**：GNU 目标下主程序的 PE 导入表里就有 `WebView2Loader.dll`
（`webview2-com-sys` 是动态链接它的）。`tauri-build` 会把它拷进构建目录，
但**不会**加进 `bundle.resources` —— 打包器根本不知道要装它。

**这是最阴的一类坑**：release 目录里一切正常，只有装完之后才出问题，
所以"我看过了，文件在啊"永远不能作为判据。

**解法**（两层，缺一不可）：

1. `tauri.conf.json` 里显式声明：
   ```json
   "bundle": { "resources": ["WebView2Loader.dll"] }
   ```
2. `scripts/sync-webview2-loader.mjs` 在打包前从 Rust 依赖目录里把它捞到
   `src-tauri/`，确保源文件真的存在（否则打出来的包会缺）

再加上 `check-installer.mjs` 打包后读 `installer.nsi` 逐文件核对 ——
`installer.nsi` 是唯一可信的清单，它列着什么，装完就有什么。

## 4. 签名密码不能靠 cmd 设置

**现象**：双击打包脚本，卡在签名那一步**无限期挂住**，没有任何输出。

**根因**：cmd 里 `set "TAURI_SIGNING_PRIVATE_KEY_PASSWORD="` 的效果是
**删除变量**，而不是"设为空字符串"。变量不存在时，Tauri 认为需要交互式输入密码，
于是等着你敲 —— 而它是被 `.bat` 拉起来的，窗口里没有任何提示。

**实测**（`tauri signer sign`）：

| 变量状态 | 结果 |
|---|---|
| 变量缺失 | **挂起 12 秒仍未返回**（在等交互输入） |
| 空字符串 `""` | 244 ms 签名成功 |

**解法**：这一步必须由 Node 完成 —— Node 里 `env.X = ""` 才是真正的空字符串：

```js
const env = {
  ...process.env,
  TAURI_SIGNING_PRIVATE_KEY: SIGN_KEY,
  TAURI_SIGNING_PRIVATE_KEY_PASSWORD: '',   // 必须是存在的空串
};
```

见 `scripts/build-desktop.mjs`。

## 5. GNU 目标下产物路径变了

**现象**：打包成功，但在 `target/release/` 里找不到安装包。

**根因**：显式指定 target triple 时（GNU 工具链就是），产物落在
`target/x86_64-pc-windows-gnu/release/...` 下，而不是 `target/release/...`。

更麻烦的是 `target/release/` **可能残留着早期其他构建方式的空壳目录**，
所以"找到目录了"不等于"找对了目录"。

**解法**：判断依据换成「`bundle/nsis/` 是否存在」，并且遍历所有 triple 目录，
不写死名字：

```js
for (const triple of fs.readdirSync(targetRoot)) {
  const nsisRoot = path.join(targetRoot, triple, 'release', 'nsis');
  ...
}
```

这样将来 Rust 加了新的目标名也不会失效。

## 6. `_up_` 编码：装好了但读不到

**现象**：资源文件确实装进了安装目录，但代码读不到它。

**根因**：`bundle.resources` 里写 `"../tools/x"`，Tauri 会把 `..`
编码成 `_up_`，实际装到 `$INSTDIR/_up_/tools/x`。运行时 `resource_dir()` 用的是
同一套规则，所以**读的一方**是对的；但如果另外用
`assetProtocol.scope` 或 CSP 白名单去放行路径，就必须自己写成
`$RESOURCE/_up_/...`，否则两边对不上。

**解法**：把"安装位置"和"配置允许的位置"当成一份契约去对账 ——
`check-installer.mjs` 的 `--verbose` 会把实际安装清单全列出来，
拿它跟你的 scope / CSP 逐条比。

## 7. 前端产物过期，静默打进旧页面

**现象**：改了源码、重新打包、装完发现**功能还是旧的**，而打包过程没有任何报错。

**根因**：早期逻辑只判断 `dist/index.html` 存在与否就决定"复用现有前端产物"。
于是改了源码没重新构建时，装进包里的还是上一次的 `dist/`。

**解法**：按**时间戳**判断，源码比产物新就重新构建：

```js
return newestSourceMtime > distIndexMtime;
```

这类问题的可怕之处在于：它在打包环节完全静默，只能等装上运行后才发现功能不对，
而那时很难想到去怀疑打包流程。

## 8. PATH 必须自己补

**现象**：编译到最后报找不到 `windres`。

**根因**：我们把 MinGW 解压在用户目录（为了免管理员权限），它**不在**用户持久
PATH 里。而 GNU 目标下 `embed-resource` 是用**裸命令名** `windres` 去调它的，
PATH 里没有就直接失败。

**解法**：`scripts/toolchain-path.mjs` 读 `src-tauri/.cargo/config.toml` 里记的
MinGW 路径，算出需要补的目录，由 `build-desktop.mjs` 注入子进程的 PATH。
这样好处是**不用重开终端**，装完环境立刻就能打包。

## 9. rustup 的 shim 是 0 字节

**现象**：装完 Rust，`cargo --version` 报不是有效的 Win32 应用。

**根因**：rustup 的 shim 是 `rustup.exe` 的副本，正常通过 hardlink 创建。
某些文件系统（或权限状态）下 hardlink 建不出来，就留下 0 字节的空文件。

**解法**：`scripts/fix-rust-shims.mjs` 检查 `.cargo/bin` 里 0 字节的 shim，
直接复制 `rustup.exe` 覆盖它（rustup 启动后靠 argv[0] 判断该扮演哪个工具，
所以复制副本就能用）。

## 10. 中文文件名进 URL 要编码

**现象**：自动更新检查到新版本，下载时报 404。

**根因**：安装包文件名含中文（`待办工作台_0.1.0_x64-setup.exe`），
直接拼进 URL 后服务端收到的路径不对。

**解法**：`gen-update-json.mjs` 生成清单时对文件名做 `encodeURIComponent`：

```js
url: `${baseUrl}/${encodeURIComponent(installer)}`
```

**更省事的做法**：把 `productName` 和 Cargo 包名都设成 ASCII
（`web2exe-app`），文件名里就没有中文，这个坑自然消失。
界面上的中文标题用 `tauri.conf.json` 的窗口 `title` 单独设即可。

## 11. NSIS 首次使用需要联网

**现象**：第一次打包卡在下载，报 `Connection Failed` / `os error 10060`。

**根因**：Tauri 的 NSIS 打包器不在 Rust 依赖里，首次使用时才去下载，
之后缓存在 `%LOCALAPPDATA%\tauri`。

**解法**：首次打包时保证网络通畅（必要时配代理）。
之后离线也能打包。`env-check.mjs` 会检查这个缓存目录是否已就绪。

## 12. 首次打包的死锁：DLL 同步依赖 Cargo.lock

**现象**：把模板复制出去、装完依赖、第一次打包，在第 4 步被拦下：

```
[x] 找不到 src-tauri\Cargo.lock
    请先在 src-tauri/ 下执行一次 cargo fetch / cargo build，让依赖解析出来。
```

可是整个流程的卖点就是"打包脚本会替你构建" —— 让人先去做一次构建，逻辑上是绕圈的。

**根因**：`sync-webview2-loader.mjs` 的职责是"让项目里的 DLL 与 Cargo.lock
锁定的 webview2-com-sys 版本保持一致"，因此它去读两样东西：

1. `Cargo.lock` 里该 crate 的版本号
2. cargo registry 里已解压的 crate 源码

**这两样在全新项目里都不存在** —— 它们都是第一次构建之后才有的产物。
于是在"第一次打包"这个最需要它工作的场景里，它必然失败。

**解法**：把"拿不到权威来源"当成**正常分支**而不是错误。

此时项目自带的 DLL 就是唯一可用的那一份（模板里预置了），直接用它继续；
等首次构建产出 `Cargo.lock`、crate 也解压好了之后，
再跑同一个脚本就会自动走正常的版本核对路径。

**推广**：凡是做"一致性校验"的脚本，都要想清楚**被校验对象尚不存在**时怎么办。
把"还没有"当成"不一致"来报错，在第一次使用时就一定是错的 ——
而第一次使用恰恰是用户对这套东西印象最深的时候。

## 13. 不在仓库里的配置文件，得有人替它兜底

**现象**：什么错都不报，只是**慢得反常**。前面的 crate 一个接一个编过，
十几分钟之后才在链接阶段倒下，报的是链接器相关的错（`could not open 'kernel32.lib'`
这一类）—— 和"正在编 Rust 依赖"这件事看起来毫无关系。

**根因**：`src-tauri/.cargo/config.toml` 是 `setup-gnu.mjs` 生成的，
内容里有**本机 MinGW 的绝对路径**。所以它不该进仓库（进了等于把别人的
`C:\Users\xxx\msys64\...` 发给使用者）—— 模板里没有这个文件是**对的**。

但它同时承担两件不能少的事：

```toml
[build]
target = "x86_64-pc-windows-gnu"     # 钉死编译目标
[target.x86_64-pc-windows-gnu]
rustflags = ["-C", "link-arg=-Wl,-exclude-all-symbols"]   # 绕开符号导出上限（第 2 节）
```

少了它，cargo 就用 **rustup 的默认 toolchain**。默认若是 msvc，那前面所有
crate 都编得过（编译阶段不需要链接器），直到最后链接主程序时才失败。
于是"配置缺失"的代价被推迟成一次**十几分钟的静默空转**，
报错位置和真正的原因隔着十万八千里。

**解法**：把"保证它存在"变成入口脚本的责任，而不是使用者的记忆负担。

- `打包桌面版.bat` → `pack.mjs` 在 `[2/5] 检查项目文件` 里发现缺配置就自动跑一次
  `setup-gnu.mjs`（幂等：只探测 MinGW 路径再写文件），补不上才停下给安装步骤；
- `启动桌面版.bat` → `launchers.mjs` 同理：原本"既无 GNU 配置又无 MSVC 链接器"
  时直接报错让人自己去跑 `setup:gnu`，现在先自动探测一次，补上了就继续；
- 想走 MSVC 路线的人用 `WEB2EXE_NO_GNU=1` 跳过这段。

**推广**：**当"不该进仓库的文件"和"必须存在的文件"是同一个文件时，
仓库缺了它，脚本就得负责补上。**

"不提交它"只是设计上正确的一半；另一半是把"运行前提"交给一个会自查的入口。
只做前一半，就会得到一种最难查的故障：**不报错，只是白等。**
